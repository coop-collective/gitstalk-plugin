## Working on this Gitstalk repository

Git is the interface; the Gitstalk MCP server is optional context. The remote is a Gitstalk host (`https://<gitstalk host>/<owner>/<repo>.git`, the same host as the repository page, as on GitHub).

Connecting git: MCP OAuth and terminal git use separate credentials. Before a first clone or on an authentication/access error (including a private-repo `not found`), compare MCP `whoami()` and `repo_list()` with the setup script's `verify <owner>/<repo>`; the stored git account may differ. Codex runs the plugin's bundled setup script directly (`../../scripts/gitstalk-setup.sh` relative to the skill directory), without Claude Code slash commands. Without a plugin, download `<web>/setup.sh` once to a temporary file (Windows: `<web>/setup.ps1`). Run `detect`; reuse the key already selected, or ask once from the `option` lines. Generate only when needed. Run `register --key <existing.pub>` or `register --agent-key <fingerprint> --agent "<socket>"`, keep the process alive while the person approves in the browser under the intended account, then `verify <owner>/<repo>` and `remote <owner>/<repo>`. An empty/null `ssh_host` means HTTPS: registration stores a token through git's helper, and the private key does not sign HTTPS requests. Do not invent an SSH URL. Only public keys are sent. Never ask for tokens in chat, put them in URLs, or print credential files. CI uses `GITSTALK_TOKEN` (the repository page, tab "Env vars").

New repository (needs the `create` scope, which setup asks for): MCP `repo_create({ name, owner?, visibility?, start?, description? })`, or `curl -fsSL <web>/setup.sh | sh -s -- create [owner/]<name> [--public] [--start <id>] [--description <text>]` (uses the token git already keeps; prints `created:` and `web:`, sets `origin`), or a first `git push` to `https://<gitstalk host>/<owner>/<name>.git` that does not exist yet. Private by default. Ask the person first before creating a public repository or one in an organization. Then commit and push the first work as a bean (`git push origin HEAD:refs/heads/bean/<short-name>`), never to the stalk. Another host (self-hosted, local, staging such as `https://gitstalk.dev`): `GITSTALK_WEB=<url>` for one run, or the script's `host <url>` to save it for every later run.

Terms: a **bean** = one small change on branch `bean/<short-name>`. **Sprout** = latest integrated state; build on it. **Stalk** = validated line. Never push to `sprout`, `stalk` or `main` (refused).

Flow (push, then keep working; never wait on your own check while you have work, never `sleep` to poll):
1. `git fetch origin sprout && git switch -c bean/<short-name> origin/sprout`
2. Work, commit. The commit message is the intent (one sentence, why, with units and assumptions stated: Clef compares them with other beans); optional trailer `Task: <id>`.
3. `git fetch origin sprout && git rebase origin/sprout` if it moved.
4. `git push origin HEAD:refs/heads/bean/<short-name>` submits the bean and returns in seconds (`-o task=<id>`, `-o intent="..."` optional). The pre-land check (about a minute) runs on the forge: start your next task at once on a new branch from `origin/sprout`. `-o wait` (blocks until the verdict) only when your very next step needs it.
5. Between steps a quick look: `git fetch -q origin '+refs/beans/*:refs/beans/*' && git for-each-ref 'refs/beans/<name>/' --format='%(refname:lstrip=2) %(contents:subject)'` (`checking`, `landed`, `green`, `red`, `conflict`, …; full verdict: `git cat-file -p refs/beans/<name>/status`). **Out of work: one blocking call the verdict wakes**, naming your beans: `git push -o bean=<a> -o bean=<b> origin HEAD:refs/wait/any` (first verdict; `refs/wait/all`: until none is checking). It stores nothing, prints each verdict as it arrives and the next step, returns at once if one is already red or in conflict, holds up to 9 minutes (`-o wait=<s>`; give your shell tool a 10-minute timeout); without `-o bean=` it covers every bean of your credential. It is also how you re-attach to a bean in check (pushing the same commit again sends nothing). A red or conflict is yours: commit your work in progress, switch to the bean, act, push it again (`git push -f …`; a new commit to a bean still in check is refused until its verdict), switch back. **Red**: failing tests, the landed bean you collided with and its intent; rebase on `origin/sprout`, fix the code. **Conflict**: rebase, keep both intents, remove all markers. **Recheck red** (`approval rules: … -> recheck`, `back to its author: recheck against <bean>`): Clef thinks your intent clashes with a bean you never saw (landed after you forked, or pushed earlier and still in check); read it (`git log origin/sprout`, or `git fetch origin bean/<name>`), fix yours so both hold if they disagree (test the combination), rebase and push with the trailer `Intent-checked: <bean>[, <bean>]`; never edit the other bean. **Inherited red** (sprout already failing): not yours; wait, rebase, retry. **Decision card**: a person decides; wait, do not work around it; relay any "Before approving: Clef also thinks it may disagree with …" to your person, never approve. Do not finish with a bean still `checking`, `red` or `conflict` unreported (`refs/wait/all` first).
6. Stacking: a task that needs your pushed, not yet landed bean may start on it (`git switch -c bean/<child> bean/<parent>`); push it after the parent lands with `git rebase --onto origin/sprout bean/<parent>`; if the parent comes back red, fix it first, then rebase the child onto it.
7. Several agents: each pushes its own beans from its own worktree, owns their reds and waits on its own beans by name; a lead does not push for them and never sleeps or polls: it starts workers in the background, ends its turn, acts on each worker's completion notification (Claude Code resumes the lead with one), and after the last one runs `git push origin HEAD:refs/wait/all` once.
8. Actions: Gitstalk runs `.github/workflows/*.yml` (GitHub's syntax). A bean reaching the stalk is a push to `main`, so `on: push: branches: [main]` runs (deploys) after your bean lands and validates; `workflow_dispatch` and `schedule` work too, `pull_request` not yet. Never say Gitstalk does not run Actions. With MCP: push, then `actions_wait_for_run(repo, bean)` (waits for the runs that landing started; failures come with the failing step and log tail), `actions_job_log` for more, fix in a new bean, push, wait again. Secrets (`${{ secrets.CLOUDFLARE_API_TOKEN }}`): `actions_secret_list` shows names; ask the person to add a missing one in Settings → Secrets and variables. Use `actions_secret_set` only with a value the person gave you for it (needs the maintain role and the opt-in `secrets` scope); never invent, read from a file or print one.

Rules: one intent per bean, keep beans small. Acceptance tests (yours and landed beans') are protected: never edit, skip or weaken them; fix the code. Update other existing tests only if your change intentionally alters their expectations (say so in the commit). After three failed rounds on one red, stop and ask. Never undo other beans' work.

Optional MCP (`gitstalk` server, OAuth; tools take `repo: "owner/name"`). It coordinates and explains; git still moves all code. **Claim before starting**: if the repository has a backlog, `task_list` then `task_claim` (refused = someone holds it; pick another; `task_claim(..., release: true)` gives back one you will not do), then `bean_open(repo, bean, intent, task?)` to reserve the name and get the branch and push commands; `work_overlaps(paths)` shows who is editing the same files. **After pushing**: `bean_status(repo, bean)` between steps gives the phase; on a red or conflict it gives the failing tests and the landed beans you collided with, their intent and files; `bean_wait(repo, bean)` blocks until the verdict wakes it, so only when nothing else is left. **Credentials**: only if git is not connected and setup is not possible, `git_credentials(repo)` returns a one-hour credential for that repository; pipe its `credential` field to `git credential approve` (with `credential.https://<gateway host>.useHttpPath true`), never into a URL, file or the chat. Decision cards and bean-to-bean conversation: `bean_context`, `bean_thread_post`, `bean_inbox_read`.

COMING: git over SSH (setup then switches the remote to `ssh://git@<ssh host>/<owner>/<repo>.git`).
